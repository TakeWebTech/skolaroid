# Figma Prototype Engineering Audit

Scope: React application generated by Figma Make for SMLS. Audit verified from source under `src/app`, styles under `src/styles`, project metadata, and route definitions. Implementation files were not modified.

## Executive Summary

This repository is a polished single-page prototype, not a production School Management and Learning System.

The app has a coherent shell, role-specific navigation, reusable UI primitives, mock datasets, local interaction state, and many routeable screens. It does not have real authentication, authorization enforcement, persistence, backend integration, server validation, production-grade error handling, or route-level permission protection.

## Classification Key

- Visual only: renders UI but no meaningful interaction beyond display.
- Prototype interaction: user can click/type and see local/toast/navigation feedback only.
- Partially implemented: local state, simple validation, or multi-step flow exists but no persistence/backend contract.
- Reusable for production: generic component or pattern can be kept with normal hardening.
- Must be rewritten: security, data, domain workflow, or integration layer is fake or unsafe for production.

## Framework And Build System

Classification: Partially implemented

- Vite 6.3.5 with React via `@vitejs/plugin-react`.
- React 18.3.1 and React Router 7.13.0.
- Tailwind CSS 4 via `@tailwindcss/vite`.
- pnpm workspace with `pnpm-lock.yaml`.
- Scripts: `dev`, `build`.
- No `test`, `lint`, `typecheck`, `preview`, CI, environment configuration, or production deployment config verified in `package.json`.
- Existing pnpm workspace includes supported native architectures for macOS and Linux after prior dependency fix.

Production gaps:

- Add test runner, lint, typecheck script, CI, env schema, build budgets, browser support policy, and release process.
- Confirm Node version support; current local runtime is Node 24.14.0.

## Design Tokens And Styling

Classification: Reusable for production with hardening

- Semantic CSS tokens exist in `src/styles/theme.css` for primary, status, card, border, sidebar, ring, and chart colors.
- Tailwind 4 `@theme inline` maps CSS variables to utilities.
- Shared components consistently use semantic tones via `StatusChip`, `StatCard`, and Tailwind token classes.
- Dark-mode token block exists but no verified UI toggle applies `.dark`.
- Global base styles set typography for html headings, labels, buttons, and inputs.

Risks:

- Some custom colors are direct hex/oklch in theme; acceptable but should be documented as design tokens.
- Several hard-coded layout classes and page-specific visual patterns remain in page files.
- No automated visual regression or accessibility contrast tests.

## State Management

Classification: Partially implemented

`AppProvider` stores:

- `role`
- `experience`
- school context
- `offline`
- `activeChild`
- `lang`

All state is in-memory and resets on refresh. Page-level state is used for drafts, toggles, wizard selections, uploads, payment status, selected records, attendance, and marks.

Production gaps:

- No server state management.
- No persistence or cache invalidation.
- No optimistic update strategy.
- No concurrency or stale-data handling.
- No typed API client.

## Backend And Data Simulation

Classification: Must be rewritten

- All domain data is mock data in `src/app/lib/mock-data.ts` or page-local constants.
- Simulated backend actions are `toast`, `navigate`, local `setState`, and one `setTimeout` payment simulation.
- No `fetch`, API SDK, database client, auth client, or real file upload was verified.

## Authentication, Roles, And Permissions

Classification: Must be rewritten

- `/signin` has no credential validation and always navigates to `/teacher`.
- App routes under `AppShell` are not guarded.
- Role switcher lets any user preview any role and navigate to that role's home.
- Role handling controls navigation labels, not authorization.
- Permission-denied UI exists in shared states, but no actual permission checks were verified.
- Sign out is a `NavLink` to `/signin`; it does not clear a session.

Security risk: Any user can directly open any route in the client.

## Internationalisation

Classification: Partially implemented

- Supported language codes: `en`, `hi`, `ta`, `te`.
- Translation dictionary uses English strings as keys with fallback to source key.
- Shell, role labels, sign-in, and some dashboard labels are translated.
- Most page content, form labels, mock data, dates, currency formatting, and toasts remain English/hard-coded.
- No route locale, pluralization, date/number/currency localization policy, RTL handling, or extraction workflow.

## Loading, Empty, Error, Permission States

Classification: Prototype interaction

- Shared state components exist: `LoadingList`, `LoadingCards`, `PermissionDenied`, `SystemError`, `NoResults`.
- `/states` demonstrates loading, empty, error, offline, success, and permission states.
- Production routes do not wire these states to real data loaders/errors.
- No global error boundary or suspense/data-loading layer was verified.

## Forms And Validation

Classification: Partially implemented

- Forms exist for sign-in, applicant portal, exam setup, fee setup, collect payment, leave, announcements, profile preferences, marks, attendance, academics setup, messaging.
- `react-hook-form` UI wrappers exist but are not used by audited page forms.
- Most forms use uncontrolled inputs with placeholders/default values.
- Required fields, schema validation, server validation, and field-level error messages are largely absent.
- Marks page validates numeric range against `MAX = 25` before submit.
- Wizard navigation allows progress through steps without required field validation.

## Responsive Behaviour

Classification: Reusable for production with hardening

- Shell has desktop sidebar and mobile bottom nav.
- Most page layouts use responsive Tailwind grids (`sm`, `lg`) and wrapping actions.
- Tables may overflow or compress on small screens unless covered by `DataTable` mobile card mode.
- No automated viewport testing was run as part of this audit.

## Accessibility

Classification: Partially implemented

Strengths:

- Many Radix primitives provide keyboard/focus behavior.
- Icon-only shell buttons often have labels, e.g. notifications/help.
- Shared state uses `role="status"` for centered state.
- Status chips include text labels, not color alone.

Risks:

- Many custom clickable `button` elements lack `type="button"`.
- Several inputs use visual `Label` without `htmlFor`/`id` association.
- Some dropdown triggers and custom buttons have no accessible name beyond icon/text composition.
- Focus behavior is mostly inherited; no page-level focus management on route changes.
- No axe, keyboard, or screen-reader audit was verified.

## Hard-Coded Data And Placeholder Logic

Classification: Must be rewritten where domain-critical

Examples verified:

- School, branch, academic year, currency.
- Students, guardians, phone numbers, fee status, attendance percentage.
- Teacher classes, assignments, announcements, tasks, timetable, results, children.
- Approvals, finance KPIs, dues, unmatched payments, admissions, exams, tenants, notifications.
- Hard-coded people such as Ravi Sharma and Aarav Sharma.
- Payment receipt uses random number.
- Many buttons produce generic toasts like "Opened", "Draft saved", "Payment recorded".

## Security Risks

Classification: Must be rewritten

- No authentication/session model.
- No route guards or RBAC enforcement.
- Role switching is client-controlled.
- Sensitive school, student, guardian, finance, and tenant data is shipped in the client bundle.
- Payment workflow is simulated and could mislead if exposed outside prototype.
- No CSRF/XSS/API security layer because no backend integration exists.
- No audit logging for approvals, marks, payments, attendance, role changes, or admissions.
- No file upload validation despite upload UI.

## Production Readiness

Classification: Must be rewritten for backend/domain layers; reusable for UI foundations

Ready to reuse:

- Visual shell structure.
- UI primitive layer.
- Semantic tokens.
- Some page composition patterns.
- State/empty/error UI components.

Not production ready:

- Auth, RBAC, data access, validation, persistence, payments, admissions, exams, attendance, finance, reporting, audit logs, notifications, messaging, offline sync, tenant isolation.

Recommended next step: treat this as a UX prototype and build a production architecture around domain APIs, permission checks, schemas, and test coverage before wiring the UI to real data.
